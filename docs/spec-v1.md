# cairn v1 spec: one place for every agent, self-hosted or hosted

Draft, 2026-11-10. v0 ([spec-v0.md](spec-v0.md)) built the linter, the store, the web service and the container image. v1 turns that into a product that runs in one place and that every agent, and every person on a team, connects to.

## Goal

- **Self-hosted:** one container. Every agent on every machine connects to its URL. Nothing is installed per machine.
- **Hosted:** the same image run as a service with accounts and plans (caps the operator sets; nothing is sold, decision 151). A user installs nothing.
- **Price:** a subscription that covers each user's worst-case cost plus a margin, well below the hosted memory products it replaces.

## What sets it apart

1. **Every claim has a receipt.** A page's claims link to the exact source lines, whatever the source: an agent's note, a meeting, a document, an email.
2. **Query and write from anywhere.** The same project is reachable over MCP from coding agents and assistant apps, and from a phone-sized web view with search and a note composer.
3. **Patterns for real setups.** Many agents with one project, many agents with many projects, and named sets of projects per use case. Each connection is limited to the projects it needs, read-only or read-write.
4. **A business's knowledge, with access levels.** Sources such as calendars, meeting notes, mail, documents, to-do lists and databases feed chosen projects. People only see the projects they may read.
5. **Setup that starts from the use case.** Each project has a kind (a repository's engineering memory, team decisions, memory for an AI feature, meetings, business documents, personal notes). After sign-in, cairn asks what you want to use it for, creates the right projects, and shows the exact command or scoped key for each agent and app.
6. **Memory that fills itself from traces.** Where model calls are already traced, a selector decides which traces are worth remembering and for which project. cairn stores verbatim excerpts with a link back to the trace, so the receipt leads to what actually happened.

## Design

| Area | Decision |
|---|---|
| Artifact | One image, two modes. `self-hosted` (default): no sign-up, no limits. `hosted`: sign-up and plans. Neither sells anything (decision 151). |
| Workspaces | Every project, key, session and grant belongs to an account, which is a workspace. The store hands out an account-scoped view, and request handlers only ever hold that view. A foreign id behaves exactly like an unknown id. |
| People | A user signs in through an identity provider and is a member of one or more workspaces, with a role. The first sign-in creates a personal workspace. |
| Access boundary | The project. Each project lists who may read it and who may write to it. Sources are routed into projects; nothing is filtered per document. |
| Connections | An agent connects with OAuth 2.1 on `/mcp` (give it the URL, approve once in the browser), or with an API key for headless use. A connection acts for one member and can be narrowed to chosen projects, read-only or read-write. |
| Human sign-in | Self-hosted: an API key, or the organisation's own identity provider over OIDC. Hosted: GitHub or Google. No passwords are stored. |
| Data | SQLite on a persistent disk, replicated continuously to object storage. One small VM behind an auto-TLS proxy. |
| Compiler | The extractive compiler by default; it needs no model. The LLM compiler (T4) was to join once a real model had been measured. Measured on 2026-11-13, it drafted the extractive page word for word in 11 of 15 runs, so it stays out of `serve`, and no plan sells a model budget, until a model step shows a measured gain (decision 76). |
| Note guard | A check when a note is written refuses notes that contain secrets or personal data patterns, per workspace policy. An audit log records who wrote, and who read when the operator asks for that (`serve --audit-reads`). |
| Project kinds | A kind carries what belongs in the project and what does not, guidance returned to the agents that use it, the sources that suit it and its default access. Kinds are data shipped with cairn, not code paths. |
| Sources | First through agents: recipes where an agent that already has a connector reads the source and writes notes with a link back. Then built-in connectors that sync on a schedule. |
| Trace source | The first built-in connector reads Langfuse. A Langfuse evaluator scores each new trace with a model connected there and names the cairn project it belongs in; cairn polls the scores, fetches the trace's observations, and stores excerpts. It targets Langfuse's current read endpoints (observations v2, scores v3). The same gateway or any OpenAI-compatible endpoint can carry cairn's own model calls. |
| Quotas | Per-plan monthly caps on writes. Reads are rate-limited in memory: a read writes nothing unless the operator asked for reads to be audited or for idle sign-ins to end. |
| Billing | Removed on 2026-11-17 (decision 151): cairn sells nothing. The plans file and its caps stay. |
| Slack | Off unless the operator switches it on (`serve --slack`). Each workspace sets up a Slack app of its own from a manifest cairn writes; a person links their Slack user with a code and then files a message as a note, writes a note, or asks the bot, each as themselves. Notes from Slack are not sent to a model unless the operator chooses that (decision 165). |
| Releases | A release is a tag that equals the version in `pyproject.toml`. The tag promotes the image `main` published for its commit, for two platforms, under its version, and makes a GitHub release with the changelog's section as its text; a release candidate (`vX.Y.Z-rc.N`) runs the same path without moving `latest` (decision 166 and the rows after it). |
| Audit trail | Every write and every change of who may do what is an event; reads are events when the operator asks for that. Each event is chained to the one before it; `serve` copies each event it stores to a logger after its write commits (an event committed just before the process dies can be missing; other commands write theirs on their own stderr). The chain shows an event that was changed (its project and detail aside) or removed from the middle of the stored trail, and not the newest events removed (decisions 171 and 179). |
| Upgrades and going back | A database records the oldest build that runs on it. An upgrade that only adds to the database can be undone by going back one image; any other needs the backup taken before it (decision 179). |
| On a cloud | `infra/gcp/` is the full set-up for Google Cloud. `infra/quick/` is one small VM on AWS or Google Cloud from three settings, running the shipped Compose files with the released image (decision 181). |

## Decisions

| Decision | Why | Rejected |
|---|---|---|
| The scoped view is a drop-in for `Store` | `compile_note`, the gate and T4's composer keep working unchanged, and the v0 contracts still hold | Passing an account id through every call |
| v0's frozen tests stay as they are | Self-hosted mode is v0's behaviour with one account; new behaviour gets new acceptance files | Editing W1 and W2 to fit |
| Versioned schema migrations (`PRAGMA user_version`), each in one transaction; a newer schema than the code knows is refused, unless the database's recorded floor says this build still runs on it (from step 31) | Per-account project names need a table rebuild, and an older image must never write to a newer database after a rollback | `CREATE TABLE IF NOT EXISTS` only |
| One database for all accounts, one search index per account | Simple backup, export and deletion. A shared index would leak word frequencies between accounts through ranking scores. | One database per account; one shared index |
| SQLite on one VM, not a managed database | The same artifact as self-hosted, a small fixed cost, and seconds of data at risk with continuous replication | Cloud Run (no durable local disk); Postgres (a second store to build and test) |
| The project is the unit of access | One rule a person can explain and audit; a source's own sharing list changes too often to mirror safely | Access lists per document or per claim |
| Agents first for sources | It works today with the connectors people already have, and needs no vendor approval. Server-side access to mail is gated by the provider's yearly security review. | Building every connector before any source works |
| Hard caps, then fall back to extractive | The margin holds whatever a user does, and a note is never refused for lack of credits | Soft limits with overage billing |
| No price before a measurement | Tokens per note, latency and gate pass rate have never been measured on a real model | Pricing from list prices and guesses |
