# Changelog

What changed for someone who runs cairn or connects an agent to it. The reasons are in [docs/decisions.md](docs/decisions.md).

Each release has a section headed `## <version> - <date>`, and the tag `v<version>`, pushed to a public repository on a commit of `main`, publishes it: `scripts/release_check.py` refuses a tag that is not the version in `pyproject.toml`, whose section here is missing, has no entry or is dated after the day the check runs (UTC), or whose version already has a release. The section is the GitHub release's text.

## Unreleased

## 0.1.0 - 2026-11-19

The first public version.

- **Memory with provenance.** Agents write notes over MCP or REST; cairn compiles them into pages whose claims are passages copied from the notes, each opening the lines it came from. A page that lost a fact, or holds a claim its source does not, is rejected and the last good version stays. A note with nothing to compile is refused, a claim stays under the heading it was written under with its whole path, two passages are folded into one claim only when their text is the same, character for character (trailing spaces and line endings aside), so notes that differ by wrapping, spacing or indentation stay two claims, and a page's body is exactly a rendering of its claims: a title is one line, whatever was sent, and a code fence a claim leaves open is closed before the next. An archive is imported only when each of its claims is the whole of every passage it cites. The checks take each claim by itself: they do not check that two passages stay next to each other on a page a model arranged.
- **Evidence for a version.** A page keeps its versions, and `evidence` answers for the version a claim was read on. Each search hit names the version of its page, so what it cited can be asked for again after the page changes.
- **Run it yourself.** One container and one SQLite file. `deploy/compose.local.yaml` runs it on one computer; `deploy/compose.yaml` adds a domain, TLS and, with `compose.backup.yaml`, a continuous backup.
- **A versioned image.** Each release publishes a container image for linux/amd64 and linux/arm64 tagged with its version, with provenance and a bill of materials. A full version such as `0.1.0` never moves; `0.1` and `latest` do. The README starts from the released image, with a build from source beside it. A release attaches `SHA256SUMS`, and each file and the image carry a build provenance attestation that `gh attestation verify` checks; the README gives the commands. A release candidate (`vX.Y.Z-rc.N`) is published as a pre-release and never as `latest`. Every change is scanned for vulnerable dependencies, for a vulnerable image on both platforms, for unsafe calls and for credentials in the history. The image is built once for each commit, on `main`, by a job that cannot write to the registry, and `main`'s run signs which digest it built for which commit; a tag builds no image: it checks that signature and promotes that digest, so a candidate and its release are the same image. A full version is never pushed twice, and after the release `latest` is moved to the highest release there is and each `X.Y` to the highest of its own. The image carries no Python package installer (pip).
- **Backups and upgrades.** The guides back up with cairn stopped, into a new folder each time, start it again whatever happened, and say how to restore a copy. An upgrade starts with that backup. A database records the oldest version that can run it: an upgrade that only adds to the database can be undone by going back to the image before it, and one that changes more cannot, and then the older image says so in one line. Going back from 0.1.0 to a build before it needs the backup taken before the upgrade.
- **People and workspaces.** Sign-in through Google, GitHub or an OIDC provider, workspaces with roles, private projects, invitations, export and deletion. On https a session's cookie is bound to the host. `serve --idle-minutes` ends a sign-in that is not used, `--require-mfa` asks an OIDC provider to show a second factor, and the allowed list is checked on every request, so once someone is taken off it their sessions, keys and agents are refused, and putting them back restores what has not expired. Revoking a key, removing a member, disconnecting an agent and deleting a set each ask first, on a page that says what stops working.
- **An audit log that can be checked.** Every write and every change to keys, agents, people and settings, with who did it. The page goes back through all of it, filters it and downloads it as CSV or JSON, and `GET /api/audit` gives the same. `serve --audit-reads` records reads too, and `--audit-keep` says how many events a workspace keeps. Each event is also one line on the logger `cairn.audit`, written after its commit: sent to a store nobody can edit, that copy keeps what it received, and it can miss an event committed just before the server dies (the other commands write their lines on their own standard error). Each event is chained to the one before it: `audit-verify` names the first event that does not follow from the one before, which is a changed event or the one after a removed one. It does not show the newest events removed, nor a change to an event's project and detail, which forgetting a note rewrites; the copy on the logger is the check for those.
- **Agents.** One address for every agent, approved once in the browser, with the projects it reaches and whether it may write; API keys for scripts, which now start with `cairn_`. Each thing an agent reads says when its note was written and whether its words came from outside the workspace, and a `graph` tool gives what the graph resource gives.
- **Sources.** Readers that bring notes from Granola, Linear, GitHub, Langfuse, Gmail, Google Calendar, Drive and Meet, and from a connector of your own. A preview of what a source would bring is offered before it is switched on; it is not required. A source starts off and reads nothing until someone switches it on, except a Langfuse source added from the command line, which reads as soon as it is added. A member manages the sources of their own account. Two sources made from one registered account whose selections cairn cannot tell apart are refused; sources added from the command line with keys of their own are not compared. The privacy guide says what each source reads. No source's notes are sent to a model the operator connects unless the operator chooses that (`<PREFIX>_SOURCE_NOTES=send`), and a project's people can allow a model, keep every model out, or leave it undecided; `<PREFIX>_UNDECIDED_PROJECTS=withhold` then sends only what was allowed. A source is reached only at an address the server checked, and one inside your own network (private or loopback) is refused unless you set `CAIRN_SOURCE_PRIVATE_ADDRESSES=allow`: a self-hosted tool on the same network needs it, a stored source keeps its settings, and the Sources page says why a run was refused.
- **From Slack.** Off unless switched on with `serve --slack`. Each workspace sets up a Slack app of its own from a manifest cairn writes; people then file a Slack message as a note, write a note, and ask the bot to find something, each as the person they linked their Slack user to, with a code shown to that person and typed in Slack. Removing the app deletes its secrets at once and forgets the notes Slack created 10 days later, whether or not Slack is still switched on then. A removal that Slack reports with a time at or before the installation's set-up is not acted on and is recorded in the audit log; the privacy guide says what removes the installation then. A note from Slack is not sent to a model that arranges pages unless the operator chooses that for Slack. It needs sign-in, a public `https://` address and a key, and is not offered under a brand yet. It is tested against a stand-in for Slack and has not been run against Slack itself.
- **Off unless switched on.** Connecting a Google account in the browser (`--google-connect`), a graph explorer (`--graph-explorer`) and a notice that an install is a private test instance (`--test-instance`).
- **Deleting.** Forgetting a note, or deleting a project or a workspace, takes it at once out of everything people and agents can read. Where an install keeps a continuous backup, the old text can stay in the database's log file until a compaction and in backup copies until they expire; the pages and guides say so, `stats` says whether a deletion still waits, and `compact --if-due` does what is left.
- **Pages a browser can use.** Tests now drive a real browser through one journey, from signing in with a key to signing out, by way of a project, a note, its page and a claim's source, search, the graph, the workspace, sources, the audit log, the notes list and forgetting a note, with an accessibility check and a narrow screen on each page it meets, and the keyboard on the page view. The page that approves an agent and the pages that link Slack are not on that journey. The skip link moves focus to the main content, and the graph explorer no longer draws names over each other.
- **A project's notes.** Each project has a Notes page that lists its notes, newest first, with the page that cites each, so a note can be found and forgotten without knowing its page; a note no page took in says so.
- **Running it.** On a database file in write-ahead mode, which the server sets when it opens one, reads no longer wait behind this server's writes or its compaction; a file that cannot be put in that mode is read under the writer's lock as before. `/healthz` answers 503 `stuck` when one write of this server has held the database for more than a minute, or a compaction for more than an hour. A compaction checks for free disk first, and a rewrite that succeeded is not repeated once it is recorded; one killed before its record runs again. One compaction runs at a time on a database, whether the server's or the command's: the second says another is running and leaves everything as it is (the command exits 3). A key that seals stored tokens can be changed without anyone connecting again (`reseal`). The note guard also refuses a URL that carries a password, an `Authorization` header with a `Bearer` or `Basic` value, and a passphrase. Every service in the Compose files has a memory and a process limit, changed in `deploy/.env`.
- **On a cloud.** `infra/quick/` puts the released image on one small VM on AWS or Google Cloud from three settings, with a certificate and backups to a private bucket, sign-in through a provider when you add its arguments, and a first boot that retries; it is validated with mocked providers and has not been applied to a real account. `infra/gcp/` is the fuller set-up for Google Cloud: containers bounded and hardened, eight alerts, nightly compaction, audit logs, and a second factor for SSH by default (review `os_login_2fa`, the boot disk's size and the bucket's soft delete before applying it to an existing deployment).
- **Limits an operator sets.** A plans file caps notes, storage, projects and requests per workspace. Nothing is sold.
- **Inside.** The schema and the web view are split into packages by step and by subject, with no change in behaviour; tests pin every schema step's statements and every route.
- **What it is not.** cairn has not been assessed against HIPAA, FERPA, COPPA or any rule like them, and as shipped it is not ready to hold health or education records about people who can be identified. The privacy guide says what is missing.
