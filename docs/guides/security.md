# Security

This guide says who can reach what in cairn, how people and agents prove who they are, what the checks on notes and pages catch, and what they do not. Each statement here rests on a test in cairn's own suite or on a numbered decision in its repository, and the [privacy guide](privacy.md) says what is kept and for how long.

## Who reaches what

- **A workspace is closed to every other workspace.** Another workspace's project, page or note id is answered exactly like an id that does not exist, over the REST API, MCP and the web pages. Search never returns another workspace's text, and its scores do not depend on it: each workspace has its own search index.
- **A project is the unit of access.** Each project has a rule saying who reaches it. A project can be private to the person who made it. Owners reach every project.
- **Three levels for a person.** A project's rule gives a person Read only, Read and write, or Read and write, and decide who reaches it. The third holds for that one project and is not a workspace role: whoever has it changes who reaches that project, their own level included, but cannot shut out its maker or an owner, and cannot delete the project or forget its notes. A workspace admin decides for a project only as any member does: as its maker, or when its rule gives them that level. Several people can be given a level at once by email address. An address that is not a member's gets nothing and no invitation, so someone outside the workspace is invited under People first.
- **Roles.** An owner manages everything, other owners included. An admin invites and removes people, manages keys and sets, and reaches projects as a member does. A member uses the projects they reach. A workspace always keeps at least one owner.
- **A connection can be narrower than its person.** A key or an agent can be limited to some projects, or to reading only. To such a connection the other projects do not exist: they are not listed, not searched, and an id of one is unknown. A read-only connection is refused every write. A key or an agent names at most 64 projects or sets; a set counts as one, whatever it holds.
- **A credential acts for the person who made it.** A session, an approved agent or a key reaches what that person reaches now, never more. When a person is removed from a workspace, their sessions, the agents they approved and the keys they made there stop working in the same step. A removed person cannot come back by signing in again: an owner or an admin has to invite them.
- **Removing is narrower than writing.** Only the person who made a project, or an owner, can delete it or forget one of its notes, and only over a session or a connection that reaches every project the person reaches and may write. Another project's note id is answered as unknown. Both ask first on the web pages, and both are in the audit log.
- **A workspace's totals are for its owners.** What a workspace has used of its plan counts every project, so only an owner, a key an owner made, or a connection that acts for no person reads it. An admin or a member gets no Usage page, and when a cap refuses their note they learn which limit, without a number or the plan.
- **Two things can show through.** Names are unique in a workspace, so someone who cannot see a project can learn that its name is taken. And a plan's cap on projects counts every project, so a member who is refused a new project at that cap, while seeing fewer projects than the cap, can tell that others exist.

## Signing in

- cairn keeps no passwords. People sign in with GitHub, Google or the organisation's own OpenID Connect provider, whichever the operator turns on.
- An email address that the provider has not verified is refused, and nothing is created.
- Each identity is tied to its provider's issuer. If a provider is replaced under the same name, a sign-in through it is refused, so a stranger with the same account number at another provider cannot become an existing person.
- A shared install can be limited to the organisation's email domains, to named groups of its provider, or to its Google Workspace domain. Any install can be limited to the people its operator names, by their whole email address. A shared workspace cannot be opened to every GitHub or Google account: cairn refuses to start with that setting.
- A browser session lasts 12 hours, unless the operator keeps sign-ins longer with `serve --session-days`; then it lasts that many days, and a use more than a day after it was made or last renewed starts them again. Its cookie is `HttpOnly` and `SameSite=Strict`, and `Secure` whenever the server's public address is https. On an https address the session cookie, and the cookie that carries a sign-in to the provider and back, have names that start with `__Host-`, so no other host under the same domain can set either. A cookie a browser still sends under the name it had before is not read, and the answer clears it. A sign-in's state is used once, and a return from the provider without the state cairn issued is refused.
- With `serve --idle-minutes N`, a session that is not used for N minutes ends, whatever its length, and the next request is answered as after any other end. It ends up to a minute late, never early: a use is recorded at most once a minute.
- With `serve --require-mfa`, a sign-in goes through only when the ID token of the organisation's OpenID Connect provider shows a second factor: `amr` lists `mfa`, or `acr` is one of the two multi-factor policies of the OpenID Provider Authentication Policy Extension. Anything else is refused, with no session made. GitHub and Google, as cairn reads them, do not say how a person signed in, so the server does not start with the option and either of them. Providers that report only method-specific `amr` values (such as `pwd` and `otp` or `hwk` without `mfa`) or other `acr` values (such as NIST `aal:2`) are refused unless the provider maps them to `amr: ["mfa"]` or one of those two PAPE policies.
- When the operator limits who may sign in, to listed addresses or email domains, the limit holds on every request, not only at sign-in. Once the server runs with a person's address no longer allowed, their sessions, the keys they made and the agents they approved are refused as ended ones. Nothing is deleted, so allowing the address again restores them. A session is checked by the address its sign-in was vouched with; a key or an agent by the address the person first signed in with. A provider's groups and a Google account's Workspace domain are known only at sign-in, so a change to them takes effect at the person's next sign-in.

## Agents and keys

- **Agents connect with OAuth 2.1.** The agent registers itself, the person approves it in the browser, and the agent proves with PKCE that it started the request. An approval code works once, for 2 minutes, and only with its verifier.
- **Tokens.** An access token lasts 1 hour and is bound to this server's MCP address and to one workspace. A refresh token lasts 30 days from its last use. Each use replaces both tokens, and presenting any refresh token the connection replaced in the last 30 days ends the whole connection, so a stolen one is caught the first time both parties use it, however often the thief refreshed first. A connection refreshes at most 6 times an hour.
- **Redirect addresses** must be https, or http on the machine itself. Anything else, a `javascript:` address included, is refused at registration.
- **Keys** are for scripts and agents without a browser. A key is shown once, when it is made. A key made now starts with a fixed prefix, so the note guard and a secret scanner can recognise one; a key made before has none and keeps working as it did. Only an owner or an admin makes or revokes keys, and a key made by a person reaches no more than that person. A key made on the server's command line acts for no person: it reaches every project and manages keys, and belongs to whoever runs the server. One made there with `--project` or `--read-only` reaches only the projects it names, or only reads, and manages no key, exports nothing and opens no web session.
- **Answers to agents and scripts are not cached.** Every answer on the REST API and on MCP says `Cache-Control: no-store`, a refusal included.
- **Every connection is listed.** Under Workspace, the Agents page lists the agents a person approved, with what each reaches, and disconnects any of them. An owner or an admin sees every agent in the workspace there. The Keys page lists the workspace's keys, and an owner or an admin revokes them.
- **What a key made.** A key made, or an agent approved, from a web session opened with a key records that key. The Keys and Agents pages say which key each was made with, and "made with a revoked key" once that key is gone. Revoking a key leaves what it made working, and says what that is. Revoking it with everything it made takes the key, every key made with it or with a key it made, and every agent approved with any of them, in one step, and ends every web session opened with those keys. Keys and agents made before cairn recorded this, and anything a person made, are never taken.

## Stored as digests only

API keys, browser sessions, OAuth codes and tokens, and invitation links are random values. cairn hands each one out once and stores only its SHA-256 digest. A copy of the database therefore holds none of them in a form anyone can use. The credentials of other services it can hold, a connected Google account's refresh token and a Slack app's signing secret and bot token, are sealed: see [below](#google-accounts-connected-in-the-browser) and [Slack](#slack). A sign-in provider's own tokens are used during sign-in and never stored.

## Google accounts connected in the browser

Off unless the operator starts the server with `--google-connect`. Then the refresh token Google gives for a connected account is stored sealed: encrypted with AES-GCM under the operator's key (`CAIRN_GOOGLE_CONNECT_KEY`), with a fresh nonce each time, and bound to the workspace, the account's name and its person, so a sealed token copied to another row does not open. The key lives only in the server's environment. The Google address, Google's own id of the account and the permissions granted are stored in clear, so a copy of the database shows who connected what, but a copy alone, or the replica in the operator's bucket, which holds the same rows, opens no token. The token that reads a service is made from it during a run and kept only in memory; no token, code, client secret or key is written to a log, an error, an answer, the audit log or an export. To take every access away, each person disconnects on the Sources page, or the operator deletes the OAuth client in the Cloud console: Google's pages say calls with its tokens then fail, and that a deleted client can be restored within 30 days; deleting the key leaves tokens no one can open, but Google still honours them until they are revoked.

What a connect or a disconnect came to is said once on the Sources page, to the person it happened to. It travels in a cookie sealed under the same key, `HttpOnly` and `SameSite=Lax`, which the page clears once it has said it; the page's address carries none of it, so a link someone else made shows no outcome.

When Google refuses to end a dropped account's permission (after the OAuth client was deleted, say), the server tries again less and less often, the wait doubling up to a day, and logs the refusal once. After 20 refusals it stops, keeps the sealed token, and logs `revoke_stopped` once. Then end the permission yourself: the person removes this server's access in their Google account's settings, or you delete the OAuth client's secret in the Cloud console, so that no token issued to it can be used with that secret again. The table of tokens waiting to be sent holds at most 10,000; past that, a dropped account's token is sent once and not kept, and the server logs `revocations_full`.

Changing `CAIRN_GOOGLE_CONNECT_KEY` without keeping the old key in `CAIRN_GOOGLE_CONNECT_KEY_PREVIOUS` makes every connected account reconnect, and leaves the permissions Google gave for the old tokens in place, with nothing here able to end them. To change it with every account staying connected: put the new key in `CAIRN_GOOGLE_CONNECT_KEY` and the old one in `CAIRN_GOOGLE_CONNECT_KEY_PREVIOUS`; restart the server; run the `reseal` command with `--google-connect`, which seals every stored token again under the new key; then remove `CAIRN_GOOGLE_CONNECT_KEY_PREVIOUS` and restart. A sealed token does not say which key sealed it, so a copy of the database does not tell which tokens an earlier key sealed. When the old key may have been seen by someone else, changing it is not enough, since a copy of the database made before then still opens with it: disconnect every connected account first, wait until Google has answered each revocation (the log says when one was not ended), then change the key.

## Slack

Off unless the operator starts the server with `--slack`. Slack calls three addresses of each workspace's install: `/integrations/slack/<install>/events`, `/commands` and `/actions`. They take no session and no key. A request is acted on only when its signature holds: an HMAC-SHA256 of its timestamp and its body under that install's signing secret, compared in constant time, with a timestamp within 5 minutes of the server's clock. Before the signature is checked, a body over 1 MiB is refused, and so is an install that does not exist or is not set up. After it, a request of another Slack workspace is refused. The signature is computed for every request that gets this far, and a request whose signature holds is never refused because of requests whose signature did not. Those that fail it are counted for each install and client address: after 20 in a minute, a further one from that address to that install is refused until the oldest of them is a minute old. An event is acted on once, whatever Slack's retries say.

The app asks Slack for four permissions: `chat:write`, to post the bot's answers; `commands`, for the slash command and the message shortcut; `users:read`, to know a Slack user's name and whether a message's author is of this Slack workspace; and `im:history`, which lets the bot read the direct messages people send it, and nothing among people.

A Slack user is linked to a person in two steps, once they have asked the bot for an address, which is theirs alone. The person opens it signed in and says yes, and is shown a code, once. The same Slack user types that code with the command within 10 minutes. So a Slack user is linked to a person only when that Slack user knew a code shown only to that person: someone who sends their address to another person gains nothing from that person's yes. A wrong code counts against the Slack user's offer, and the fifth deletes it; a code typed by any other Slack user is dead. A link is never moved to another person: a Slack user linked to someone stays linked to them until it is undone. The limit is said plainly: someone who talks you into sending them your code acts as you, which is why the page that shows it says to give it to no one.

Answers are private: the slash command's and the shortcut's are shown only to the person who asked, and a direct message is answered in that direct conversation. An answer is built from the asker's reach, as a search of theirs: a project they do not reach gives nothing, not even a count.

The signing secret and the bot token are sealed under the operator's key, `CAIRN_SLACK_KEY`, so a copy of the database opens neither. To change it with every install staying set up: put the new key in `CAIRN_SLACK_KEY` and the old one in `CAIRN_SLACK_KEY_PREVIOUS`; restart the server; run the `reseal` command with `--slack`; then remove `CAIRN_SLACK_KEY_PREVIOUS` and restart. cairn's Slack client calls nothing at Slack that reads a conversation's history: it asks whose a token is and who a user is, posts the bot's answers, and answers through the address a signed request gave.

## The note guard

Before any part of a note is stored, cairn checks its text and every field that comes with it. By default it refuses a note that holds:

- a private key block;
- an AWS access key id;
- a GitHub, Slack, OpenAI, Anthropic, Google, Hugging Face or Groq token;
- a JSON Web Token;
- one of cairn's own agent tokens, or one of its API keys made with the prefix (a key made before has none, and is caught only as a value assigned to a name such as `api_key`);
- a password in a URL, such as `postgres://user:password@host`;
- an `Authorization: Bearer` or `Authorization: Basic` header with its value;
- a value of 12 characters or more assigned to a name such as `password`, `secret`, `token` or `api_key`; after `password` or `passphrase`, a quoted value counts whatever it holds, words and spaces included.

A refused note leaves nothing behind. The answer names the rule and the line; the audit log names the rule. Neither holds what matched. A workspace's policy can also refuse personal data (an email address, a phone number written with `+` or in the North American way, such as `(415) 555-0199`, a US Social Security number, a payment card number, an IBAN, and a date of birth or a medical record number written after its label, such as `DOB:` or `MRN`), or check nothing. The workspace page says which policy is in force, in words, to everyone in the workspace, and its owners and admins choose it there; each change is in the audit log. When the operator runs cairn with a guard of its own, that guard decides for every workspace and the page says so.

The guard matches patterns. It does not recognise a name, a postal address, free-text health details, a date of birth or a record number without its label, keys of other providers, or a secret that was split, encoded or reworded. A note that passes is not thereby free of secrets.

## What the checks on pages catch

cairn checks every page against its notes before it saves it, and keeps the last good version when a check fails. Forgetting a note is the one write that is never refused: it rewrites the pages that cited the note from the passages that remain, and a claim that could not stay leaves the page while its note stays stored. An import takes each version's claims and citations as its archive holds them and writes its body again from them, checked as a save is; a claim an earlier version of cairn folded from passages that differ only by white space is accepted as that version made it.

- Every claim on a page is a passage of a note, copied word for word, and cites the lines it came from.
- A version, a flag, a number, a path or a line of code in a passage the page cites is on the page.
- A number, a flag or a path in a claim is in the lines it cites.

When the operator connects a model, it only puts a page's claims in order and says which ones repeat each other. It answers with claim numbers, and cairn builds the page from text it already holds, so the model writes no word of it. The page says which model arranged it.

The checks take each claim by itself. They do not check that two passages that stood next to each other in a note are next to each other on a page a model arranged, so a sentence that leans on the one before it can stand apart from it. Each claim still opens its own lines in its note, where the order is the writer's.

A page's body is the notes' own Markdown, one note after another, so one note's Markdown can change how the body shows another's: a setext heading puts the claims after it under that heading; a link definition shows nothing and turns a matching bracketed word in any other claim into a link to its address; when two notes define one label, every use in the body takes the first definition; and a claim that begins with indentation, after a claim that ends in a list, is read as part of that list's last item, so text that alone is indented code can read there as a paragraph or a heading. In a body this version writes, a code fence does not run from one claim into the next: the body closes it where its claim ends, sixteen such fences on a page at most. A note that would leave a seventeenth open is stored but kept off the page, which keeps its last version; and forgetting a note is never refused: a claim that would then leave such a fence open leaves the page with the forgotten note's, and its own note stays stored. A page an earlier version stored with more such fences than a body closes is read with every claim exact and one sentence in its body's place, never with the fence running on; an export copies a version's Markdown as stored, so such a fence stays in the exported `.md` until the page is saved again. Each claim's own text and source are exact in the claims list and in the web view, which shows each claim by itself. Read the body with raw HTML off, as the web view does: with it on, an HTML block a note opens and does not close (a comment, a script, a processing instruction) holds every claim after it.

What the checks do not do: they compare text, not meaning. A page holds what the notes said, and if a note was wrong, its claim is wrong in the same words. A note's text is quoted material to cairn, never an instruction, but an agent that reads a page still reads what the note said.

## Who wrote what an agent reads

- **cairn does not decide whether a note is an instruction.** It stores what was written and returns it word for word. It does not hold a note back for a person to check, and it does not guess which sentences are commands.
- **Every recalled line names its writer.** Each hit of `recall`, each claim of `page` and each passage of `evidence` says who wrote the notes behind it: a person by name, never by email address; a key by its label; an agent by the name it registered with; a source by its name; or the server's command line. A web session opened with a key writes as that key. A note stored before cairn recorded writers says its writer was not recorded. Each also says when its note was written (`written_at`); a hit or a claim that cites several notes, when the newest was.
- **Outside text is marked.** A note a connected source brought in was written by whoever can write at that source, so its lines are marked `outside`, and the web pages say "outside text" beside it. A note stored before cairn recorded writers is marked so when it came in via a source. In what `recall`, `page` and `evidence` answer, a message filed from Slack is marked `outside` too: its writer is the person who filed it, its `filed_message` says so, and its words are the message's author's, whom the note's heading names. A note typed with the Slack command is the person's own.
- **Agents are told once.** When an agent connects, cairn tells it that what recall, page and evidence return is text someone wrote down, to treat as information and never as instructions.
- **No mark of trust.** cairn does not rank writers: a note from a key that reaches one project is named as that key's, like any other key's, with no mark of how far the key reaches.
- **What an operator can do.** Keep notes of different trust in different projects, and give each agent only the projects it needs. Give an agent that only reads a read-only key or approval. Give each source a project of its own. The notes of every kind of source the server reads are not sent to the model that arranges pages unless the operator allows it.

## The web pages

- Every page except a project's **Graph** page runs no script. By default `serve` loads one script on that page alone, cairn's own, by a nonce made for that page and with its hash, and the page still works without it; with `serve --no-graph-explorer` no page runs a script. The pages allow styles, images and fonts from cairn itself and nothing else, and cannot be shown inside another site's frame.
- The two typefaces, Atkinson Hyperlegible Next and Atkinson Hyperlegible Mono, ship with cairn under the SIL Open Font License 1.1; their licences are served at `/static/fonts/atkinson-hyperlegible-next.OFL.txt` and `/static/fonts/atkinson-hyperlegible-mono.OFL.txt`.
- A form posted from another site is refused.
- Pages are not cached, and a page's address is not sent to other sites.
- An address that is not a page answers "There is no page at this address" for everyone, signed in or not.
- A project's page links its **Graph**: its pages, the claims on them, the passages those claims cite and the notes the passages come from, drawn by the server and listed again as text below the drawing. By default under `serve` it shows one view at a time (the pages, the notes, a page's claims or a claim's passages), at most 20 to a batch, with **Next batch** for the rest, and each note has a page of its own; with `--no-graph-explorer` the page shows at most 20 pages on one static sheet. A key reads at most 20 pages of the graph at `GET /api/graph?project=<name>`, an agent at the MCP resource `graph://project/<name>/<limit>`, and a project out of reach is answered as one that does not exist.

## Logs

- **The audit log** records every write and every change to keys, agents, people, settings and sets of projects (a set made, changed or deleted, with its projects: changing a set changes at once what the keys and agents limited to it reach), with who did it. A reader sees only the projects of a set they reach. It never holds a note's text. Owners and admins read it under Workspace, then Audit log, a part at a time, filtered by what was done, by project and by who, and download what they see as CSV or JSON; a key that manages the workspace reads it at `GET /api/audit`. Each export of the workspace's notes and pages, and each download of the log, is an event of its own, with who and when. It keeps the newest 100,000 events of each workspace, unless the operator starts the server with `--audit-keep N`, or `--audit-keep all` for every event; the page says the number in force. It also records each web session opened, by the person or with the key, and how, and each agent approved, as the act of whoever approved it, when they approve it, whether or not the agent then connects.
- **Reads go to the access log**, one line per read on the server's own output, whether an agent, a script or a person in the web view made it: who called, what, which project and the status. It never holds a query, a note's text or a credential, and a refused request is logged without what it presented. When the operator starts the server with `--audit-reads`, reading a page, a note, a claim's evidence, a search and a graph are each an event of the workspace's audit log too: who read, what kind of read, the project, and the page or note read, never the words searched or any text. It is off unless given, since each read then costs one more write.
- **A copy of the audit log the server cannot change.** The running server writes each event it stores as one line on its output, once the event's write has committed: a JSON object with the same fields as the stored event, on a logger of its own, and never a note's text. The copy can miss an event: one committed just before the server's process dies, and one a command of the command line stores, such as `key-create` or `import`, which writes its line on its own standard error instead, kept only where the operator keeps that output. Keeping those lines where nobody can change them, such as a bucket locked against deletion, is the operator's set-up, and such a place keeps what it received: the log in the database is rewritten when a note is forgotten or a project deleted, which takes out the page names made from notes, and loses its oldest events past the number kept.
- **The audit log shows when it was changed.** Each stored event carries a value that chains it to the event before it in its workspace, and the operator's command `audit-verify --db PATH` names the first event that no longer follows from the one before, by its number and time; pruning the oldest events keeps the chain checkable. Someone who can write the database file can rewrite the whole chain, which is why the server writes a copy of the events it stores on its output (above, with the events that copy can miss). An event's project and detail are outside the chain, because forgetting a note must be able to take a page's name out of them. Removing the newest events leaves a shorter chain that still follows, so that, too, shows only against that copy. Against the copy, a change shows only for an event the copy holds.
- The server prints no request addresses, so no query string reaches a log.
- **The shipped proxy** (Caddy, for a hosted install) does log each request's address. Its configuration cuts every query string and the token of an invitation link out of that address, and drops the headers that carry a key, a session or the page a request came from. An operator who replaces the proxy has to do the same.

## What a workspace can take

- A plan with a storage cap bounds what a workspace takes on disk, not only the bytes of its notes. Its passages are bounded with it, one per 40 bytes of the cap: each paragraph, list item or other block counts one, and the headings stored with every passage and heading count one more for each full 40 bytes. Its pages' older versions take at most four times the cap. On every install the headings above a passage take at most 400 bytes in all, and a note's headings may outnumber its passages by at most eight; a note past either is refused.
- On every install a note holds at most 30,000 facts: numbers, dates, versions, paths, links, flags and pieces of code. A note with more is refused before anything of it is stored, and the answer gives the count and the bound, never the note's text.
- So a workspace takes at most 30 times its storage cap, plus 1,500 bytes for each note it holds. cairn's tests fill workspaces to their caps with the costliest shapes of note found, the smallest notes there are among them, and hold each to both parts. The second part is what every note costs whatever its length (its record, its line in the audit log, its headings); the plan's cap on notes a month is what bounds how fast it grows.
- On every install a page holds at most 2,000 claims, so saving one more note onto a page never grows without end. A note that would pass it is refused before it is stored, and the answer says to file it under another topic. A page also holds at most 400,000 characters of claims, since every save lints and indexes the whole page again; a note that would take its page past that is refused the same way, and the answer says which bound it met. A page that already held more when this bound came stays as it is: it can still be read, and notes can still be forgotten from it, but it takes no more notes, and the answer says so.
- An imported page must be what cairn would have written from its notes: its claims are the text of the lines they cite, its body is what cairn writes of them, and its figures are a short list of numbers and words. Anything else is refused and nothing is imported.

## What cairn leaves to the operator

- cairn does not encrypt its database file. Disk encryption, and who may log in to the machine, are the operator's.
- Backups are the operator's: the shipped configuration replicates the database to a storage bucket the operator owns.
- A source's credentials, such as a Langfuse key, are environment variables of the server, so only the command line registers an account, or adds or removes a source from a config; a person makes sources from an account registered for them, and owners and admins from the workspace's. The database never holds a third party's key, except the sealed tokens of Google accounts connected in the browser and the sealed secrets of a Slack app, when the operator switches either on ([above](#google-accounts-connected-in-the-browser), [Slack](#slack)).
- A source sends its credential only over `https`, or `http` on this machine. Before each request, the server checks the written address or every address the name resolves to. It always refuses link-local, cloud metadata, multicast, unspecified and broadcast addresses. Other addresses that are not globally reachable require `CAIRN_SOURCE_PRIVATE_ADDRESSES=allow`. The connection uses a checked IP, keeps the original HTTP and TLS host name, and follows no redirects. One range stays refused with `CAIRN_SOURCE_PRIVATE_ADDRESSES=allow` too: the local-use translation range `64:ff9b:1::/48`, which each network lays out its own way, so a server on an IPv6-only network cannot read an IPv4-only source through such a translator. The server's calls to Slack go through the same check.
- Anyone with the database file and the machine can read every workspace in it. The rules above govern people and agents that come through cairn.
- cairn limits each client's sign-ins and agent registrations (20 registrations an hour from one address, unless the operator set another number), and bounds its own memory and its calls to the sign-in provider. A flood from many addresses is the operator's to stop, at the proxy or the network; while it lasts, new sign-ins can be refused. People already signed in are not affected.
- cairn also limits the wrong keys and tokens each client address presents: once an address has presented 30 in a minute, a wrong one from it is answered 429 in place of 401 for the rest of that minute. A correct key or token is never refused by this limit, from any address.
- These limits are counted in the server's memory, so they start again when it restarts; for a limit that outlasts a restart, put a reverse proxy's or the cloud's own rate limit in front of cairn. Each server process keeps its own, and they start empty after a restart: they are kept in memory on purpose, since writing a row for every failed attempt would let anyone who can send failing requests keep the database's one writer busy. What stands behind them when they are gone: a key is 256 bits from the system's random source, so guessing one is not a matter of how often one may try, and signing in is the provider's.
